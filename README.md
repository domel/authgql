# AuthGQL research prototype

This directory contains a self-contained Python prototype.
It is an executable semantic model and a security-test harness, not a complete GQL
implementation or a production access-control system.

The current implementation is aligned with the terminology and relevant baseline
semantics of ISO/IEC 39075 (GQL).

The project has no runtime dependencies beyond the Python standard library.
Development checks are configured in `pyproject.toml`, and GitHub Actions runs
the unit tests, Ruff, and mypy on Python 3.10--3.12.

The distinction matters: GQL defines principals, session authorization
identifiers, implementation-defined privilege sets, request-level authorization,
and condition class 42, but does not standardize roles, a concrete privilege
vocabulary, authorization targets, or their administration. Statements such as
`CREATE ROLE`, `GRANT`, `DENY`, and
`CREATE AUTHORIZATION POLICY` below are therefore **AuthGQL extensions**, not
syntax claimed to exist in core GQL. Standard GQL spellings are retained where the
prototype implements them, notably `SESSION_USER`, `START TRANSACTION`, and the
`NODETACH`/`DETACH DELETE` distinction.

## What is implemented

The prototype implements the following end-to-end path:

1. a persistent authorization catalog with role inheritance, user-role
   assignments, grants, denials, grant options, grantors, policies, dependencies,
   and a revision number;
2. transactional administration of roles, privileges, and policies, including
   `RESTRICT` and conservative transitive `CASCADE` behavior;
3. static derivation of `ACCESS`, `TRAVERSE`, `READ`, `INSERT`, `DELETE`, `SET`,
   and `REMOVE` obligations from the supported query AST;
4. pre-execution object-level checks with privilege implication and deny-overrides;
5. a side-effect-free, three-valued policy compiler for a GQL expression subset,
   including correlated `EXISTS { MATCH ... }` graph predicates;
6. guarded fixed-length and bounded quantified path expansion, with every node,
   edge, and endpoint checked before enqueueing or binding materialization;
7. separate topology (`TRAVERSE`) and property (`READ`) authorization;
8. authorization before `OPTIONAL MATCH`, `EXISTS`, filtering, ordering, and
   `COUNT`, so hidden candidates cannot affect these logical operators;
9. statement-atomic `INSERT`, `SET`, `REMOVE`, `DELETE`, and `DETACH DELETE`
   execution on a prospective graph clone;
10. old-state `USING` and new-state `WITH CHECK` enforcement before the clone
    replaces the visible graph;
11. a transaction-level authorization snapshot, staged data/catalog changes,
    `READ ONLY` enforcement, `COMMIT`, and `ROLLBACK`;
12. read-only catalog views, redacted for ordinary authorization identifiers;
13. an explainable guarded-plan description and security instrumentation;
14. an internal authorized-view route used to cross-check guarded read results;
15. a reproducible hospital scenario, deterministic evaluation script, and 25
    unit tests.

## Architecture

| File | Responsibility |
|---|---|
| `authgql/model.py` | In-memory property graph, graph cloning, adjacency indexes, and GQL-compatible plain versus detach deletion behavior. |
| `authgql/catalog.py` | Roles, inheritance, grants/denials, targets, delegation, revocation, policies, dependencies, snapshots, and catalog views. |
| `authgql/parser.py` | AST and parser for the supported GQL query/update subset. |
| `authgql/analyzer.py` | Static privilege obligations and guarded logical-plan description. |
| `authgql/policy.py` | Compilation and evaluation of pure policy predicates. |
| `authgql/authorization.py` | Object-level checks and fine-grained deny-overrides/closed-scope policy combination. |
| `authgql/executor.py` | Guarded matching, expressions, aggregation, atomic updates, metrics, and the internal materialized-view cross-check. |
| `authgql/session.py` | Stateful console surface, authorization administration, introspection, and transaction snapshots. |
| `authgql/cli.py` | File/REPL command-line interface. |
| `evaluate.py` | Reproducible deterministic security-validation workload. |

`authgql_console.py` is a compatibility entry point for the modular CLI. It no
longer contains a second authorization engine.

## Authorization decision, step by step

For a session authorization identifier `u`, action `a`, and resource `x`, the
prototype evaluates authorization in this order.

### 1. Object availability

The session can select only a graph loaded into its graph registry. This models the
ISO/IEC 39075 distinction between availability/name resolution and
permission. Availability of a graph does not itself mean that an induced subgraph
is available.

### 2. Static obligation check

The analyzer walks every supported query constituent before evaluation. Node and
edge patterns produce `TRAVERSE`; properties in patterns, `WHERE`, `RETURN`, and
`ORDER BY` produce `READ`; data-modifying clauses produce their corresponding
write obligations. Obligations are deduplicated and matched against catalog
targets before execution starts.

`MATCH` implies `TRAVERSE` and `READ`. The catalog's `UPDATE` object-privilege
family is a convenience umbrella over `INSERT`, `DELETE`, `SET`, and `REMOVE`; it
is not a core policy action or a GQL `UPDATE` statement. `ADMINISTER` implies the prototype's
authorization-object `CREATE`, `ALTER`, and `DROP` actions.

For every applicable object fact:

- a matching `DENY` wins over every matching `PERMIT`;
- otherwise at least one matching `PERMIT` is required;
- graph target `*` is the prototype's administrative wildcard;
- targets may be graph-wide, node-label-scoped, single-edge-label-scoped, or
  property-scoped.

`USER alice` means the authorization identifier `alice`, not an underlying
principal. Privilege facts and individual policy grantee entries retain their type,
so a user is not treated as a same-named role. The compact policy descriptor cannot
represent both `USER x` and `ROLE x` in one policy grantee list and rejects
that artifact-only case. Role creation/membership, `DENY`, policy administration, and
revocation require `ADMINISTER`. A non-administrator can delegate only a permit
granted directly to the same authorization identifier with grant option;
role-derived permissions cannot support delegation. `WITH GRANT OPTION` therefore
requires one explicit `USER` grantee, and `DENY` cannot carry it. Delegated facts
record their grantor, and support follows only covering action/target edges.
`RESTRICT` rejects removal when a matching downstream fact exists; `CASCADE`
removes the matching support chain even if equivalent authority remains elsewhere.
`REVOKE DENY` removes denial facts, whereas ordinary `REVOKE` removes permit facts.

### 3. Fine-grained decision

Policies are selected by graph, action, grantee/effective role, enabled state, and
resource selector. Combination is fail-closed:

1. if no enabled policy is applicable to the requester, action, and selector, the object decision is
   sufficient;
2. a matching deny predicate blocks on `TRUE` or `UNKNOWN`;
3. otherwise at least one matching permit predicate must be `TRUE`;
4. if policies are applicable but no permit predicate is true, access is denied.

This is why selectors are important. A policy declared `ON GRAPH hospital NODES
Patient` closes only the `Patient` scope; it does not accidentally close traversal
of `User`, `Hospital`, or `Diagnosis` nodes.

For `READ`, the protected resource is conceptually `(element, property-name)`, but
`RESOURCE` remains bound to the base node or edge. Consequently, a `NODES Patient`
policy applies to every patient property, while a property-scoped privilege fact
can narrow the object decision. An applicable property denial overrides broader
permits. Labels of a traversal-authorized element are treated as non-confidential;
`READ` protects property values.

Missing policy clauses compile to `true`. `INSERT` uses `WITH CHECK`, `DELETE`
uses `USING`, and `SET`/`REMOVE` use both. In an applicable permit this leaves that
phase unconstrained; in an applicable denial it denies that phase unconditionally.
The closed-scope rule still requires a matching permit. Policy creation rejects
mixed phase classes, `INSERT USING`, and old-state-only actions with `WITH CHECK`.

### 4. Guarded evaluation

Graph scans and expansions first test labels and the requested edge label, then run
`TRAVERSE` authorization before a candidate is enqueued. An edge is usable only
when the edge and its endpoint pass. Property dereference calls `READ` before the
value is returned to filtering, sorting, grouping, projection, or a function.

Projecting a whole node, edge, or path does not silently serialize its backing
property map. The JSON interface emits graph-element reference values using only
`{"kind": "node|edge", "id": "..."}`; clients must request every property with
an explicit, guarded dereference such as `p.age`.

`OPTIONAL MATCH` null-extends only after its authorized match space is empty.
Correlated `EXISTS` is evaluated over that same authorized space. `COUNT` counts
authorized bindings only.

The executor reports logical-result and guard-flow counters.
`denied_before_enqueue` counts candidates rejected at the trusted guard before
they enter a frontier or binding. Candidate lookup itself occurs inside the trusted
in-memory layer, so this instrumentation does not describe index,
adjacency-buffer, cache, or storage-engine touches and is not an independent proof
of traversal-touch safety.

### 5. Atomic write checks

For a modifying statement, the executor:

1. evaluates its authorized match/read part;
2. runs `USING` against every old-state target;
3. clones the graph and stages the complete delta;
4. runs `WITH CHECK` against every post-state resource in the prospective graph;
5. computes any authorization-checked `RETURN` result against that prospective
   graph; and
6. replaces the visible graph only if every check and result expression succeeds.

Multi-node/edge `INSERT` stages the entire pattern before policy evaluation, so a
policy can inspect another element created by the same statement. An inserted edge
may attach to an old endpoint only if that endpoint is traversal-authorized. A
failure leaves the original graph unchanged.

Plain `DELETE` has implicit `NODETACH` behavior, as required by GQL: all incident
edges must also be explicitly designated, otherwise the prototype raises GQL
status `G1001` with a redacted message. Explicit deletion targets are
policy-checked before this ordinary data-rule validation, so a denied target yields
`42000` without exposing incident topology through `G1001`. `DETACH DELETE` adds
incident edges to the deletion set, authorizes each one, and deletes edges before
nodes.

## Policy predicates

`using` and `with_check` in catalog JSON may be Booleans, the legacy restricted
JSON predicate AST, or a string in the prototype's pure GQL-expression subset. New
examples use the GQL form.

The enforcement engine binds:

- `RESOURCE` to the candidate in `USING`, and to the old element in `WITH CHECK`
  (`NULL` for insertion);
- `NEW_RESOURCE` to the proposed post-state element in `WITH CHECK`;
- `SESSION_USER` to the GQL session authorization identifier;
- `PARAM('name')` to a session/request parameter;
- `HAS_ROLE('name')` to effective role membership.

Supported predicate constructs include Boolean composition, comparisons, `IN`,
label tests such as `RESOURCE:Patient`, property access, `IS [NOT] NULL`, `ID`,
`ELEMENT_ID`, `COALESCE`, `PROPERTY_EXISTS`, and correlated bounded
`EXISTS { MATCH ... [WHERE ...] }` patterns.

Predicate evaluation preserves GQL's three truth values. A comparison with a null
operand returns `UNKNOWN`; `NOT`, `AND`, `OR`, and `IN` propagate it according to
three-valued logic. A permit matches only `TRUE`; a denial blocks on `TRUE` or
`UNKNOWN`. Evaluation faults fail closed: a `TRAVERSE` fault rejects that
candidate without an exception, whereas a strict `READ` or write guard raises a
redacted `42000`.

Example:

```gql
CREATE AUTHORIZATION POLICY local_patient
ON GRAPH hospital NODES Patient
FOR TRAVERSE, READ
TO ROLE clinician
EFFECT PERMIT
USING (
  EXISTS {
    MATCH (u:User {login: SESSION_USER})-[:WORKS_AT]->(h:Hospital)
    MATCH (RESOURCE:Patient)-[:TREATED_AT]->(h)
  }
);
```

Policy evaluation is trusted and does not recursively invoke the protected user's
policies. It reads the raw current graph for `USING` and the raw prospective graph
for `WITH CHECK`, not a requester- or owner-filtered view. Predicates are parsed
into an AST; Python `eval`, user-defined functions, mutation, I/O, and unbounded
expansion are not available. The catalog records the creating authorization
identifier as owner and validates acyclic named policy dependencies. Enforcement of
owner `POLICY REFERENCE` privileges for general catalog dependencies is not
implemented and is therefore not part of the prototype's evidence.

## Trust boundary and observable guarantees

The modeled attacker is an authenticated authorization identifier that can issue
any statement in the supported subset, choose parameters, repeat requests, and
observe returned bindings, status codes, transaction outcomes, and its redacted
catalog view. The session binding, catalog, parser/analyzer, policy compiler and
evaluator, guarded executor, and in-memory graph are trusted. Unredacted policy
text is restricted by catalog views. For reproducibility, this research CLI emits
validation counters with query results; those counters are outside the modeled user
observation and would require administrator-only exposure in a deployment.

Within that boundary, guards keep denied topology out of executor queues and
bindings, prevent protected properties from feeding expressions, and publish
updates only after all checks pass. The prototype does not normalize all error
distinctions and does not claim resistance to timing, cache, memory, plan-shape,
resource-usage, persistence, or tracing channels.

## Transactions and authorization snapshots

Use standard GQL transaction command spelling:

```gql
START TRANSACTION READ WRITE;
-- queries and updates
COMMIT;
```

At `START TRANSACTION`, the session clones the visible graphs and fixes a clone of
the authorization catalog. Later external grant/policy changes do not affect checks
inside that transaction, and the authorization identifier cannot change. Data and
catalog changes are staged independently. Administrative statements can refer to
catalog objects staged earlier in the same transaction, and `SHOW AUTHORIZATION`
renders those staged descriptors. Permission to inspect the full tables and all
data authorization decisions still use the start snapshot, so staged grants do not
authorize their creator before commit. On
`COMMIT`, graph clones replace their live counterparts; catalog commit also checks
the original revision to avoid overwriting a concurrent authorization change.
`ROLLBACK` discards both kinds of staged state.

In `READ ONLY` mode, static object obligations and graph access are checked first.
A static authorization failure therefore raises `42000`; if those checks pass, a
modifying statement raises `25G03` before dynamic `USING` or `WITH CHECK`.

The console's `SET USER` is explicitly a test-harness meta-command. It is not a GQL
session command and is rejected during an active transaction.

## Supported surface syntax

### AuthGQL authorization extensions

```text
CREATE ROLE role
DROP ROLE role [RESTRICT|CASCADE]

GRANT [ROLE] role TO [USER|ROLE] member
REVOKE ROLE role FROM [USER|ROLE] member

GRANT action [, action ...]
  [PROPERTIES {p, q}]
  ON GRAPH graph [NODES label | EDGES label]
  TO [USER|ROLE] grantee [, ...]
  [WITH GRANT OPTION]

DENY action [, action ...]
  [PROPERTIES {p, q}]
  ON GRAPH graph [NODES label | EDGES label]
  TO [USER|ROLE] grantee [, ...]

REVOKE [DENY | GRANT OPTION FOR] action [, action ...]
  [PROPERTIES {p, q}]
  ON GRAPH graph [NODES label | EDGES label]
  FROM [USER|ROLE] grantee [, ...]
  [RESTRICT|CASCADE]

CREATE AUTHORIZATION POLICY name
  ON GRAPH graph [NODES label | EDGES label]
  FOR action [, action ...]
  TO [USER|ROLE] grantee [, ...]
  EFFECT PERMIT|DENY
  [USING (predicate)]
  [WITH CHECK (predicate)]
  [DEPENDS ON {dependency, ...}]

ALTER AUTHORIZATION POLICY name ENABLE|DISABLE
DROP AUTHORIZATION POLICY name [RESTRICT|CASCADE]
SHOW AUTHORIZATION
EXPLAIN AUTHORIZATION query
```

`WITH GRANT OPTION` requires exactly one explicitly typed `USER` grantee. Omitting
`RESTRICT|CASCADE` selects `RESTRICT`. Policy action lists must come from one phase
class: old-only (`TRAVERSE`, `READ`, `DELETE`), new-only (`INSERT`), or dual
(`SET`, `REMOVE`). The parser also records the target graph as a mandatory policy
dependency.

`GRANT` and `REVOKE` occur in GQL's lexical word set, but the concrete statements
above remain proposed AuthGQL syntax. AuthGQL-specific words are treated as
contextual, non-reserved words in authorization-statement positions.

### Executable GQL subset

```text
USE GRAPH graph
MATCH pattern [, pattern ...]
OPTIONAL MATCH pattern
WHERE expression
RETURN expression [AS alias] [, ...]
ORDER BY expression [ASC|DESC] [, ...]
LIMIT non-negative-integer
SET variable.property = expression [, ...]
REMOVE variable.property [, ...]
[NODETACH|DETACH] DELETE variable [, ...]
INSERT node-or-directed-path-pattern [, ...]
FINISH
START TRANSACTION [READ ONLY|READ WRITE]
COMMIT
ROLLBACK
```

Patterns support directed, incoming, and undirected matching; one edge label per
edge pattern; node/edge property maps; and bounded quantifiers such as `*1..5`
(capped at 12 hops). Because the subset has no explicit path-mode prefix,
expansion follows GQL's default `WALK` behavior and permits repeated nodes and
edges. The `*m..n` form is a documented legacy parser shorthand; the prototype
does not parse GQL's `{m,n}` form, path-variable bindings, or GQL path values.

The JSON field historically named `type` represents the prototype's **single edge
label shorthand**. It must not be confused with a GQL edge type, which is a schema
type defined by an exact label/property signature and endpoint types.

## Running the prototype

Python 3.10 or newer is supported; the reported validation was run with Python
3.10.12. There are no third-party runtime dependencies.

Run the supplied hospital demonstration as clinician `alice`:

```bash
python3 AuthGQL_prototype/authgql_console.py \
  --graph AuthGQL_prototype/examples/hospital.graph.json \
  --catalog AuthGQL_prototype/examples/hospital.catalog.json \
  --user alice \
  AuthGQL_prototype/demo/demo.authgql
```

The equivalent module entry point, when the prototype directory is on
`PYTHONPATH`, is:

```bash
cd AuthGQL_prototype
python3 -m authgql \
  --graph examples/hospital.graph.json \
  --catalog examples/hospital.catalog.json \
  --user alice \
  demo/demo.authgql
```

Run one query and compare it with the internal materialized-view route:

```bash
python3 AuthGQL_prototype/authgql_console.py \
  --graph AuthGQL_prototype/examples/hospital.graph.json \
  --catalog AuthGQL_prototype/examples/hospital.catalog.json \
  --user alice \
  --compare-reference \
  --command "MATCH (p:Patient) RETURN COUNT(p) AS patients"
```

Without a script or `--command`, the CLI starts a semicolon-delimited REPL. Use
`--parameter name='"value"'` for context parameters, `--save-graph` and
`--save-catalog` for explicit persistence, and `--keep-going` to continue a test
script after a denied statement.

## Catalog and graph formats

The examples are the canonical format documentation:

- `examples/hospital.graph.json` stores graph name, nodes, labels, properties,
  directed edges, their single label shorthand, and endpoints;
- `examples/hospital.catalog.json` stores role inheritance, user-role assignment,
  privilege facts, policies, dependencies, metadata, and revision.

Both `PropertyGraph` and `AuthorizationCatalog` provide `load`, `save`, `to_dict`,
`from_dict`, and `clone`. Duplicate element IDs, missing endpoints, unknown inherited
roles, cyclic role graphs, duplicate policy names, unknown policy dependencies,
and cyclic policy dependencies fail closed during loading or mutation.

## Tests and reproducible validation

Run all 25 tests:

```bash
python3 -m unittest discover -s AuthGQL_prototype/tests -v
```

Run static and type checks used during development:

```bash
ruff check AuthGQL_prototype
mypy AuthGQL_prototype/authgql AuthGQL_prototype/evaluate.py
```

Run the deterministic evaluation workload:

```bash
python3 AuthGQL_prototype/evaluate.py
```

It covers guarded fixed and quantified paths, hidden `EXISTS`, authorized
aggregation, protected property failure, and rejected `WITH CHECK`. For every
read case it compares executor output with an internally materialized authorized
view. That route shares the parser, expression evaluator, authorization layer, and
query operators with guarded execution; it is a consistency check, not independent
validation. Protected-property behavior is asserted separately as
`42000`, because deleting a property from a materialized view would model absence
rather than the strict profile's denial. The report omits wall-clock fields and
includes reproducible guard-flow counters instead. In particular,
`denied_before_enqueue` records the tested interpreter branch; it is not a claim
about physical storage access.

## Deliberate limitations

The implementation does **not** claim GQL parser or engine conformance. In
particular:

- only a small linear-query subset is parsed; full GQL composition, `LET`,
  `FOR`, `FILTER`, `OFFSET`, set operators, multi-path patterns, path prefixes,
  path-variable bindings and path values, shortest-path search, and explicit
  `TRAIL`, `SIMPLE`, and `ACYCLIC` path modes or search prefixes are absent;
- the graph JSON format permits exactly one edge label and calls it `type` for
  backward compatibility; general edge label sets, label expressions, graph types,
  node/edge type descriptors, schemas, and constraints are not implemented;
- only `COUNT` aggregation is implemented, and mixed grouped/aggregate projection
  is intentionally rejected;
- `SET` and `REMOVE` cover properties, not labels or whole property maps;
- procedure definitions/calls, `EXECUTE`, security-invoker/definer profiles, and
  policy-owner `POLICY REFERENCE` enforcement are not executable;
- policy patterns are bounded and use a deliberately restricted expression set;
- a policy grantee list cannot contain both a user and role with the same spelling,
  although those tagged identities remain distinct across privilege facts and
  separate policies;
- catalog dependency names other than `policy:name` are recorded but cannot be
  resolved against a full GQL catalog;
- transaction snapshots are single-process prototypes; graph write conflicts,
  multi-session isolation, durable logging, crash recovery, and distributed or
  federated enforcement are absent;
- the internal materialized-view route cross-checks logical results using shared
  components; it does not independently validate the semantics or cover storage,
  cache, timing, optimizer, or other side channels;
- traversal-touch counters instrument this executor, but they are not a proof of
  noninterference or of behavior in another storage engine;
- authentication, credential handling, identity federation, and authorization-
  identifier creation remain outside scope, matching the boundary in ISO/IEC 39075.

Never use this prototype to protect production data. Its purpose is to make the
paper's semantics inspectable, executable, and falsifiable.
